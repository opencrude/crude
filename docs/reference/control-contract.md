# Crude Semantic Control Contract

> Status: Current runtime reference — native tools, retained core routing and external MCP are implemented; complete UI-family and platform acceptance remain open.

## One API and its owners

`types/control` owns neutral descriptors, targets, requests, inspection nodes and
results. `types/control/catalog.go` is the command catalog; core owners bind exact
runtime DTO schemas. `core/` authenticates/adopts callers, resolves actual effects,
serializes admission and journals mutations. Domain services own effects;
`coreclient`, `shellport/remote` and the registered TUI Host route shell intents
through Update, never Paint. `cranemcp` adapts this same API, not a second control
engine. Native agents discover `crude_commands`, then invoke `crude_control` using
the returned command ID and exact arguments. Discovery grants no authority.

The catalog includes settings, sessions, managed executions, shared documents,
files, Git, Local History, terminals, bounded performance/runtime diagnostics and
shell tree/panes/tabs/editor/panels.
A descriptor's presence does not prove every product component supports every
verb. Inspect live availability and exact schemas; unsupported controls fail
explicitly. [Managed executions](managed-executions.md) describes isolation and
integration. Existing [core protocol](core-client-protocol.md) ownership remains
in force.

Discovery matches by words: commands containing every word of the query are
returned (words in the command ID rank first); when none contains them all,
commands are ranked by how many they contain. Simple plurals match.

MCP connections and their secrets are agent-manageable for the user through
`capabilities.inspect` (read), `capabilities.set_secret` (write),
`capabilities.remove_secret` (delete), `capabilities.set_enabled` and
`capabilities.set_tool_enabled` (write), `capabilities.save_connection`
(execute, since it can define a local launch) and
`capabilities.remove_connection` (delete). They run through the same owner as
Settings, follow the session's Manual/Auto Review/YOLO policy, never return
secret values, and mask secret, authorization, header and environment values
in approval prompts. Enabling an external server's tool for the first time
still uses `mcp_request_access`.

Session settings are session-owned fields of the same settings catalog. Besides
model, thinking and permission fields they include `multi_agent`,
`code_intelligence` (the agent `lsp` tool) and `max_sub_agents` (0 = inherit the
app/workspace value). Each explicit set/remove is applied live through the
session owner, with last write wins and no expected configuration revision;
it never rewrites application or
workspace layers. Language-server launch and resource fields
(`lsp.languages.<id>.command`, arguments, environment, settings, initialization
options and resource limits) are human-owned: an agent may toggle a configured
server's `enabled` field but cannot change what runs.
Workspace `analysis` and `analysis.trust` writes and removals are human-only.
They never inherit application/session authority; a session Code Intelligence
opt-in cannot bypass Static only. Native-root binding metadata is generated by
the workspace preference owner and is not in the editable settings schema.

## Exact identity and admission

Targets retain logical workspace, optional execution/session/resource identities
and, for shell operations, exact client ID plus positive attachment epoch. Agent
callers retain their current agent/run; external callers retain their admitted
client. Caller fields are attribution, not authentication or human approval.
The core checks current attachment/run and refuses foreign sessions, stale epochs,
resources and revisions. Domain operations may run headless; shell operations
never select whichever shell or tab happens to be focused.

`composer.inspect` is an explicit own-draft read, never part of generic shell or
performance inspection. It reports `pending_pastes` from the existing Send
barrier, so an automation caller can observe attachment readiness before one
submission rather than sleep for a guessed RTT or repeat an uncertain send.

Preconditions retain revision (including explicit zero) and positive open epoch.
Owners recheck at effect time, not merely discovery. Component identities carry
lifetime/edit generations; close/reopen and edit/undo ABA cannot reuse a prior
inspection. Modal/deck policy applies to semantic actions as to pointer input.
Generic `shell.control` first resolves `shell.describe_control` and requires the
exact `expected_action`; actual effect and human-only metadata are re-resolved
before execution. Generic controls or key injection cannot authorize consent,
permission, secrets or privilege changes.

Memory, Board and the capabilities modal resolve actions against their
live owners. Overflow choices carry their actual selected action's effect:
inspection/refresh/fetch is read, local navigation/curation is write, and an exact
retirement confirmation is delete. Clipboard export is explicitly unavailable
through this generic path without its own host-effect receipt. An admitted read
does not require a mutation approval token on a second resolution.
Capability registration toggles retain human-owned settings authority through
generic controls; opening, searching and selecting never grants activation,
server launch or tool access.

`panel.show` is navigation only. Showing an empty terminal panel does not launch
a PTY; creation requires `terminal.open`/`terminal.create` and its Execute
authorization. Performance navigation reuses the existing dashboard lifecycle.

Effects are read/write/delete/execute/communication/authority, never implicit
read. Manual/Auto Review/YOLO authorize eligible exact operations within explicit
denials and owner ceilings. Human-only authority is not reviewer-eligible.
`crude_control` runs on the agent's serial permission lane, so a Manual-mode
mutation reaches a human prompt instead of resolving as a denial. The prompt
and reviewer risk use the resolved effect (write, delete, execute) and show the
exact arguments as readable `path: value` lines. Chat rows project
`crude_commands` as command/effect/description entries and `crude_control`
receipts by state, fault, identities and output, never a raw JSON envelope.
Settings Save considers **all dirty drafts**, including off-page editors; an
ordinary page does not sanitize an authority-bearing pending draft.
Trust drafts remain authority-bearing when their page is hidden; generic keys,
pointer controls, Save or Reset cannot authorize them.
Field-level settings paths, schema and observation revisions are discoverable; account entities and
security authority use their human-owned paths, and MCP connections and secrets
use the `capabilities.*` commands. Questions retain
agent versus external-client answer provenance, never fabricated human input.
See [settings layers](settings.md).

Ordinary question drafts navigate through a distinct review stage. Only an exact
admitted `question.submit` or `question.cancel` action can resolve the backend
question; `question.next` is local navigation and never a decision receipt.
Generic question controls preserve agent/external attribution and cannot approve
permissions or bypass human-owned authority.

## Receipts, uncertainty and shell presentation

Results distinguish admitted, committed, applied, pending_decision, partial,
failed and uncertain, with request/operation/resource identities and faults.
Domain commitment and shell mounting are separate: a terminal may exist while
its exact originating shell detaches. Such partial/uncertain evidence is not a
successful visible mount. `applied` acknowledges the shell owner, not proof that
physical terminal pixels were displayed.

`terminal.open` additionally waits off Update for the created resource's
post-request inventory publication before acquiring control and mounting it.
Immediate `terminal.show`, picker and placement reads cannot outrun that
publication. Cancellation keeps a returned resource identity as partial retained
evidence, never permission to create a replacement. This shell's synchronous Close
fence or a newer removal prevents late create/control completions and stale
picker/placement actions from mounting it again.

Both domain and shell mutations use the original caller's durable receipt.
`operation.receipt` observes its original `request_id`; transport clients also
expose `request.receipt`. Do not replay an unknown effect or retarget it after
reconnect. Changed payload under an existing request identity fails closed.
Cancellation after admission is not proof of no effect. Read-only inspection
releases transient channel accounting; the **256 retained shell mutation receipt
cap is not a read-call budget**. Current outstanding/queued-byte limits still
apply. Pending/partial/uncertain receipts require explicit reconciliation.

Pure read completion does not advance workspace revision. Both domain and shell
result boundaries validate semantic JSON and transport limits before final reply
or receipt publication. Invalid/oversized owner output produces a bounded fault,
not a dropped reply and eventual timeout. Valid operation/resource identities
survive; a known mutation is partial rather than falsely failed with no effect.

Generic control authorization and effect-time admission each perform their own
read-only contextual resolution. These inspections have distinct transport/reply
identities, because the first result can reach its waiter before the shell's reply
acknowledgement releases client accounting. They never reuse a mutation-derived
read ID, replay an effect, or change the original mutation/receipt identity.

Original mutation receipt observation precedes new contextual resolution, so an
acknowledged Save/Close remains recoverable after its component unmounts. The
same ID with different input fails; recovering a receipt never creates another
window or repeats a domain effect. Async Memory mutations and Board read markers
retain known committed evidence as partial if their original panel cannot present
it. Entity Apply validation failure must retain the draft, not report applied.

## External MCP startup

`crude --mcp [project]` exposes newline-delimited stdio MCP through the normal
private core connection (or strict SSH bridge), without starting an interactive
shell or modifying its console. `--mcp-effects` is an immutable explicit startup
effect list, default `read`, drawn from read/write/delete/execute/communication.
Authority cannot be granted. `--mcp-shell` and positive `--mcp-shell-epoch` must
be supplied together to bind a shell; a headless launch has no shell authority.
Launch scope cannot be widened by later tool calls.

The four external tools are `crude_commands`, `crude_control`, `crude_shells`
(informational, at most 128 identities; cannot change launch binding) and
`crude_receipt` (original request receipt, not re-execution). Native and external
controls share catalog, owner fences and actual-effect authorization. This is
Crude semantic control, not a bundled desktop driver. External computer-use is
provided only by a user-selected MCP integration and its real OS/vendor permissions.

## Value and inspection bounds

| Boundary | Limit |
|---|---|
| Identity/cursor | 65,536 UTF-8 bytes; no controls; nonblank when required |
| Input/output schema | 64 KiB each |
| Individual input/output/value JSON | 64 KiB |
| Requested inspection page | Explicit 1–128 records |
| Serialized inspection page | 64 KiB, including qualified identities/cursor |
| Actions per node/resource IDs per result | At most 128 |
| Retained shell mutation receipts | 256; read inspections do not accumulate here |

Inspection nodes are flat, owner-redacted semantic records with role, accessible
name, lifetime/revision, state, available actions and optional terminal-cell bounds.
They are not screenshots or arbitrary reflected Go objects. Cursors bind current
inventory/lifetime. Clones detach nested values. Per-value limits do not imply an
aggregate frame, memory, latency or cost guarantee.

Byte-limited pages retain the exact first-unreturned Host cursor instead of
truncating a fully exported collection. A mounted control is addressed directly,
even when more than 4,096 offscreen collection rows precede it. Source hashing
is still proportional to the observed inventory; ordinary unobserved paint/ticks
do not build that inventory. Human unmount/replacement still invalidates an
already observed lifetime.

## On-demand diagnostics

Normal agent work does not sample diagnostics. The common prompt contains one
short discovery/narrowing rule; schemas and returned pages supply query-specific
guidance only when used. All commands below are Read effects, exposed through the
same native/MCP gateway and immutable external launch grants.

| Command | Existing owner and coverage |
|---|---|
| `performance.core` | Core process registry, OS resources and canonical Performance findings. Works headless. |
| `performance.shell` | Exact originating shell registry/resources; never substitutes a focused peer or the core. |
| `diagnostics.core` | Retained runtime counts, clients/carriers/grace, workspace capacities, topic publication/applied ACK metadata and own transport request pressure. |
| `diagnostics.workspace` | Status Center issues/operations/notices/agents, LSP health and capability runtime state. No service launch, notice read-marker change or panel opening. |
| `connection.inspect` | Small exact-shell identity/time, current carrier/RTT/state and safe notice. Not replica freshness or provider health. |

Performance arguments default to `{}`: a compact summary, 120-second window and
no history points. `seconds` is 1–300; `points` is 0–60 (history requires 1–60).
`page.view` selects summary, series, history, tables, events or resources;
`page.filter` narrows metric name/group/owner. Runtime views are summary, clients,
workspaces, replication, requests and listeners. Listener configuration is distinct
from actual live endpoint observations. Workspace views are summary, issues,
operations, notifications, agents, lsp and capabilities. Metadata explains units,
retention, percentile estimation, incomplete process trees and CPU warmup.

Read dense output like a large file:

1. Start with a small summary or a narrow view/filter.
2. Pass the returned `next` object as `arguments.page`, omitting seconds/points.
3. Continue using that immutable `snapshot_id`; offsets count records. Do not mix
   pages from fresh samples. A fresh read omits snapshot_id and starts at zero.
4. Invalid ranges, changed selectors and expired/foreign snapshots fail with
   recovery guidance. Empty/end pages are valid; past-end offsets are not.
   A too-small byte budget names the first unreturned record and supplies an
   exact same-snapshot retry request with the maximum budget. It never silently
   skips that record or forces a fresh sample to recover readable evidence.

| Diagnostic read boundary | Limit |
|---|---|
| Default page | 12 records / 16 KiB actual encoded JSON |
| Maximum page | 64 records / 48 KiB, below the 64 KiB control-value ceiling |
| Observation retention | 2 minutes, 16 observations / 16 MiB encoded evidence per Store, at most 4 per exact owner |
| Single retained observation | 4 MiB encoded evidence; narrower selectors required above it |
| Concurrent fresh collection | 4 per Store; no background polling or persistent diagnostic cache |
| Runtime inventory | At most 2,048 records, explicit source partial flag when omitted |
| Actor inspection | 50 ms per actor, four workers with a shared 750 ms inventory deadline |

These are delivery/encoded-retention limits, **not a hard process-heap ceiling**:
owner snapshot construction and detached Go objects also consume memory/work.
Expired evidence is rejected and reclaimed on fresh collection; no eviction timer
runs during ordinary work. A restart loses live observation IDs, not journalled
tool-result evidence. A complete page stream covers its selected record set, not
all historical telemetry or all OS permissions. Missing, unobserved, folded,
overwritten, partial and warming-up measurements are not healthy zeroes.

`types/inspect` owns bounded immutable read evidence only; it owns no metrics,
authorization or product state. Each process registry remains authoritative.
`perfdata` derives the same findings/headlines for dashboard and agents from the
same capture. Proven Linux boot identity and process creation identity qualify
resource deduplication; different or unknown hosts have separate totals. Hostname
or bare PID never proves equivalence.

Core-owned diagnostics and exact-shell read routing do not queue behind the
workspace actor they may need to diagnose. The existing gateway rechecks current
native run/root-session ownership through Collaboration, or retained client and
immutable external effects/shell grant. No second authorization registry exists.
Mutations and workspace-state commands retain actor admission. Diagnostic workers
are bounded/cancelled and joined before core database shutdown; per-actor read
admission also fences and joins saved-workspace retirement. Native snapshot
keys include RunID (runtime epoch alone is insufficient); shell keys also retain
the original attachment and workspace generation.

Runtime details are scoped to the current attached workspace; safe core-wide
counts/client capacities follow the existing per-user core trust boundary. Other
clients' request payloads/results and resume secrets are absent. Without an exact
transport caller, request metadata is explicitly unavailable, not borrowed from a
peer. This does not introduce multi-tenant security or a fleet-wide monitor.
Workspace output is an explicit bounded status projection, not an arbitrary Go
object/config export; long text has omission markers and actions are counts, not
effect payloads. Owner-authored status text is evidence, not instructions or a
universal credential-redaction guarantee. MCP stderr uses its owner's redaction.

## Evidence and limits

`types/control`, `core/control_*_test.go`, `coreclient/control_test.go`,
`shellport/remote/control_test.go`, `cranemcp`, `app/mcp_control_test.go` and
`tui/ui/control*_test.go` cover contracts, real transport/admission, receipts,
component generations and native ownership. TUI journey tests cover selected
shells/decks/forms; they are not exhaustive UI-family acceptance. A real framed
control fixture has sequential Linux 160×40 and 80×24 captures for tree hide,
split editors, one actual retained PTY and persisted workspace Tab size=8;
independent test-success files and exit-zero evidence accompany inspected images.
Native Windows 160×40 and 80×24 captures now cover this same framed fixture,
including explicit terminal close, verified unmount and persisted settings, with
independent success markers. This is selected-flow acceptance, not every UI family.
macOS arm64 remains cross-compilation rather than native interaction acceptance.
Remaining family work, final repository gates, native-platform and
SSH/distinct-host acceptance must be reported separately. Neither runnable APIs
nor these test names establish universal automation or completion of the active
[implementation plan](../plans/agentic-control-and-capabilities.md).

Diagnostic tests additionally cover dense native and MCP paging, successive-run
rejection, unchanged canonical status/drafts/revisions, exact shell attribution,
late switch/shutdown delivery and actual native/external gateway reads while the
current actor is blocked. These local fixtures do not establish distinct-host,
live-model or native-pixel acceptance; those runs need separate evidence.

The opt-in diagnostic harness is described in [validation](../guides/validation.md#live-diagnostic-acceptance).
Its local and distinct-host journeys deliberately use the same production
App/composer, exact model, gateway, registry and retained core. Synthetic load is
labelled `diagnostic_fixture`, not passed off as product telemetry. Provider
outputs are probabilistic: successful acceptance runs are observations, not a
promise that every model query or future workload is correct.

| Integrated gates | Full normal suite/build, full race suite, lint, wiregen freshness, design/docs audits and unchanged benchmark gate passed. Focused wire/auth/topic fuzz campaigns passed; relevant neutral/transport packages cross-built for Windows amd64 and macOS arm64. |

The harness exposed its own guessed-paste delay, confusion between root-turn and
agent-lifetime completion, and unqualified done-event race; readiness/generation
facts now fence those assertions. Production regressions found in the broader
checks included fast-exit SSH output lifetime, shutdown late writers and briefly
contended catalog reads. The catalog lock regression failed before the correction
and passed with paced, read-only SQLite retries inside the existing deadline.
On-demand diagnostics identified an idle agent/empty queues during the first
remote harness stall instead of inventing a provider or actor failure.

This is selected-flow acceptance on Linux, not new native Windows/macOS visual
coverage, uninterrupted active-run survival across a crash, arbitrary-length
conversation reliability or a promise of correct reasoning from every future
model response. The extended journey explicitly requests compaction; it does not
establish every automatic-compaction threshold or every provider failure mode.
