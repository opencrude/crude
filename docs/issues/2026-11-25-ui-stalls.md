# UI stalls in dense sessions

> Status: Two repeatable paint costs fixed. Long live Update, paint and console-write stalls still need evidence from the new build.

## What the live shell recorded

Windows shell build `b4a22d658c9b71db`, November 24 local time. `performance.shell` recorded a 115.146 ms `ui.update` after `viewmodel.TickMsg`; its sampled stack was at the unchanged-source check in `SyncFromWorkspace`. Another 71.460 ms Update sample was at a nil check in `handleWorkspaceOpenPromptInput`. Neither sample measures CPU spent at that line. Four child agents were busy and test builds were running. The core snapshot showed separate service work: `git.snapshot` reached 242 ms, and the slowest recovery checkpoint took 25 ms. Those measurements do not establish a blocking call in the shell.

The 48-hour shell archive returns a 63.176 ms `ui.view` sample at 23:19:49 in `clearIntersectingSpans` → `FillRect` → `Host.PaintRegions`, and two more samples there (63.171 and 72.448 ms). It also retains a 53.482 ms `render.write` at 23:19:48 and a later 125.204 ms write. Terminal writes are measured separately from paint and frame handoff. A 103.917 ms paint sample landed in an environment-variable read for the workspace title. No one sample says how much CPU each function used. The live shell showed 2.6 GiB as “Shell memory,” but that was a tree total and included other processes.

## Reproduction and changes

Native Windows amd64, Go 1.27.4, i7-9850H, `GOMAXPROCS=2`. Three runs each, CPU profiles separate the sampled work from waits; other workspace activity was not fully isolated. The `go test` benchmarks use the product's existing sync, projection and grid writes, not a terminal emulator. Times are not machine gates.

| Timed stage | Before | After |
|---|---:|---:|
| `BenchmarkDenseChildPaneSync`, four unchanged 2,001-row children | 301–378 ns; 0 B, 0 allocs | 412–486 ns; 0 B, 0 allocs (same sync path) |
| `BenchmarkDenseChildPanePaint`, alternates active tool dots on four compact panes | 10.93–12.72 ms; 11.82 MB, 71,536–71,538 allocs | 16.4–20.4 µs; 11,967 B, 92 allocs |
| `BenchmarkFillRectDenseSpans`, retained 160×48 buffer, both edges cross wide cells | 115.6–118.6 µs; 0–1 B, 0 allocs | 15.0–16.5 µs; 0 B, 0 allocs |

- The warm sync path already compares source identity, generation and version in constant time. The benchmark does not reproduce a code stall at that line. It keeps a zero-allocation gate. A new source or missing journal still needs a fresh projection. No artificial frame skipping was added.
- In the old compact pane, one active dot caused all tool rows to rebuild at each phase. That builder consumed about 55% of sampled process CPU. A separate 7.32 MB per paint on four static children came from the header copying full transcripts to read the last row. The header now reads that row directly. The compact projection retains settled rows and stores alternate ink only for the active rows; the blink preserves layout and scroll. First projection, changed source, and width changes still do real work.
- About 69% of the old dense-fill profile was in the span-clearing scan. A rectangular overwrite now preserves the style of the uncovered parts of crossing spans without retaining any old glyph or link. It skips clearing the interior twice and copies rows from the first filled row, with no new buffer.

## Reading a new report

Open **Performance → Save report**. If the dock is too narrow, focus Performance and press **s**. The Overview shows the shell's own resident memory and CPU; the Resources tab labels totals as process trees. The report includes the producer's build and a nearby sample's exact UTC interval. It lists process CPU (100% per logical core), host CPU (100% across the host), the Go scheduler's maximum recorded wait, the longest GC pause, and summed GC-assist CPU time. For a watchdog capture, compare its wake-up delay after the 50 ms threshold with the stall time and the sampled stack. A process-wide sample can precede a stall. Missing or stale data is not zero, and none of these readings proves the cause or reports the UI goroutine's exact CPU time. The report omits private operation labels, raw errors and file contents; it does not include a full runtime trace.

A high host load and late watchdog support investigating CPU pressure. A large GC pause supports investigating allocation churn. A consistent stack with a reproducible CPU profile supports a code fix. A slow terminal write is separate from those stages. Repeat on the new build before claiming that a specific live outlier is gone.

## Verification

Native `scripts/tuishot.ps1` used `TestPerformanceSaveReportNativeCapture` with the production App, event-loop observer, and an isolated home. At 160×40, the mounted **Save report** button saved and opened the Markdown. At 80×24, the focused **s** shortcut saved and opened it. A deliberate 150 ms Update wait produced a trace naming the test function while the watchdog woke 515 µs and 313 µs late. The desktop report showed 0% shell CPU, 34% host CPU, a 656 µs Go scheduling wait and a 1 µs GC pause in the preceding one-second interval. That low CPU with a deliberately blocked Update illustrates why the sampled stack, wall time and process context must be read together. Neither export contained the planted private label. Both capture windows closed.

The three new allocation gate cases pass. Focused package tests, the viewmodel's dense-pane and dashboard journeys, `go vet` and changed-code lint pass. The complete performance sweep is left for a quiet machine. This does not establish that the original live wall-clock outliers have disappeared.
